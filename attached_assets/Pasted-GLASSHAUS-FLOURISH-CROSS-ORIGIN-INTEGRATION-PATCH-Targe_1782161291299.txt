CONTEXT — WHAT JUST SHIPPED

In the build that just completed, you extended the site-scoped
tracking system to HFHC. The architecture now is:

  — portal_visits and access_tokens tables both have a
    site TEXT NOT NULL DEFAULT 'glasshaus' column
  — /portal/ping accepts a site field, defaults to 'glasshaus'
    if absent
  — Admin dashboard has a persistent site selector in AdminNav
  — Site values currently in use: 'glasshaus' and 'hfhc'
  — Email notifications include [Site] in the subject line

HFHC integration was easy because HFHC lives in the same
monorepo and proxies /api requests via the Vite dev proxy
(same-origin). The usePortalPing hook fires fetch calls to
"/api/portal/ping" which the proxy routes to the shared API
server.

CONTEXT — WHY FLOURISH IS DIFFERENT

Flourish is deployed at flourish-nairb1969.replit.app — a
separate Replit project in my account, NOT in the Glasshaus
Ecosystem monorepo. This means:

  — Flourish cannot use Vite's proxy pattern to reach /api
  — A fetch call to "/api/portal/ping" from Flourish would hit
    Flourish's own backend, not the Glasshaus shared API server
  — To send pings to the shared API, Flourish must make a
    cross-origin HTTPS call to the full public URL of the
    Glasshaus Ecosystem API
  — The Glasshaus Ecosystem API must be configured to accept
    CORS requests from the Flourish origin

The Flourish deployment is currently password-protected via
Replit's deployment shield. That's deployment-level
authentication, separate from any application-level auth.

THIS PATCH'S SCOPE — MINIMAL

QUESTIONS FOR YOUR ASSESSMENT

Before writing any code, please respond with:

1. CORS configuration approach
   Recommend whether to maintain a hardcoded allowed-origins
   list in the API server code, OR move it to an environment
   variable so future partner properties can be added without
   redeploys. Given that we anticipate Atrium, BlissBeacon,

2. Flourish project access
   Can you access the Flourish Replit project from this
   session, or do you need me to grant access first? If you
   need access, what specifically (deployment password,
   project sharing invite, code paste, etc.)?

3. Cross-origin auth posture
   Currently /portal/ping does not require authentication —
   any client can ping it. For Flourish, this is fine for
   pure visit logging. But: should we add a lightweight
   shared-secret (HMAC or simple API token) to the cross-
   origin pings to prevent random internet abuse of the ping
   endpoint? Recommend tradeoff.

4. Failure mode on cross-origin
   If the Glasshaus API is down or unreachable, the Flourish
   ping fetch call will fail. Should Flourish:
     a. Log the error and continue silently (current Glasshaus
        pattern — fire and forget)
     b. Retry with backoff
     c. Queue failed pings in localStorage and resend later
   Recommend.

5. URL configuration
   Flourish needs to know where to send pings. Recommend:
     a. Hardcoded constant in the Flourish code (e.g.,
        const API_URL = "https://glasshauswellness.com/api")
     b. Environment variable in Flourish's Replit secrets
     c. Both — env var with hardcoded fallback
   Given that Flourish is a separate Replit project, env vars
   may be the cleaner option for non-secret config.

6. Verification approach
   Once the build is done, how do we verify the integration?
   Specifically: how do we trigger a Flourish visit without
   logging in through Replit's deployment password each time?
   Recommend a test flow.

7. Backward compatibility
   The existing HFHC and Glasshaus integrations should be
   completely unaffected by this change. Confirm that the
   CORS update doesn't accidentally break the same-origin
   path that HFHC and Glasshaus use.

8. Anything else you would flag.

Please respond with your full assessment of these eight items
BEFORE writing any code in either project.

SECTION 4 — STRATEGIC NOTES
=======================================================================

Why this integration matters now:

The Glasshaus admin dashboard currently sees two of the four
properties in the ecosystem. Adding Flourish makes it three.
Bringing all four under unified observability is the operational
foundation for the Bold Horizons Phase 2 launch (Flourish is
the first paying ARR target) and for investor diligence (the
"one control surface governs the entire ecosystem" story).

Why cross-origin is the right pattern for now:

Migrating Flourish into the monorepo is a larger task with its
own risks (deployment history, in-flight work, build pattern
differences). Cross-origin integration via the public API
preserves Flourish as a working standalone deployment while
still bringing its traffic into the unified dashboard. If a
future architectural decision warrants the migration, that's
a separate project. This pass keeps options open.

Why the CORS architectural question matters:

This is the first cross-origin integration. The choice of how
to manage allowed origins (hardcoded list vs. env var)
establishes the pattern for every future partner property.
Doing it right once is cheaper than redoing it for each new
property.

What success looks like:

  — A real visit to flourish-nairb1969.replit.app generates
    a portal_visits row with site='flourish'
  — The row appears in /admin/portal when filtered to
    "Flourish"
  — A notification email arrives with subject "[Flourish]
    Portal visit"
  — Existing Glasshaus and HFHC pings continue to work
    unchanged
  — No console errors or CORS preflight failures in the
    Flourish browser console
